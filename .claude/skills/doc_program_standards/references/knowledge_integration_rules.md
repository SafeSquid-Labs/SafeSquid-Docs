# SafeSquid Knowledge Integration Rules

Use the internal knowledge base to improve accuracy and enterprise relevance without creating contradictions.

## What to extract

- Product behavior and bounded capability statements
- Deployment patterns and topology guidance
- Security posture and standards posture
- Buyer pain points that sharpen problem framing
- Operational caveats and known gaps

## What not to do

- Do not copy internal framing that overstates current capability.
- Do not convert roadmap items into present-tense product features.
- Do not flatten confidence labels.
- Do not duplicate the same knowledge across many docs when one linked reference page is better.

## How to place knowledge in docs

- Put threat and risk context in the opening sections.
- Put deployment assumptions near prerequisites and setup.
- Put evidence details in validation and troubleshooting.
- Put governance, rollout, and monitoring advice near production readiness steps.

## Conflict avoidance

- Compare new claims against existing docs in the same topic area before publishing.
- Harmonize terminology across all affected pages.
- If two pages overlap, define one as primary and link from the secondary page.

## Rewrite priority

Start where readers carry the most deployment risk:

1. Deployment planning
2. SSL inspection
3. Authentication
4. Proxy mode and client onboarding
5. Clustering and high availability
6. Reporting and SIEM
7. DLP and malware controls
8. DNS security
9. Disaster recovery
10. Troubleshooting hubs
