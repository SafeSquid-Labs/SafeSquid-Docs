## The production path

Use this sequence for a first deployment:

<Steps>
  <Step title="Plan the control path">
    Complete [Deployment Planning](/getting_started/deployment_planning). Record topology, capacity, routing, DNS, NTP, identity, certificate trust, logging, rollback, and ownership decisions.
  </Step>
  <Step title="Install one approved platform">
    Select the documented appliance, Linux, cloud, virtual, or hybrid path. Do not route production users until the installation checks pass.
  </Step>
  <Step title="Connect one pilot client">
    Use [Connect Your Client](/getting_started/client_configuration/connect_your_client) and confirm a new transaction appears in the expected SafeSquid access log.
  </Step>
  <Step title="Activate and establish trust">
    Activate the instance, deploy the approved Root CA to managed pilot endpoints, and verify HTTPS browsing without certificate warnings.
  </Step>
  <Step title="Apply controls in a known order">
    Add inspection, identity, access, malware, and data controls one stage at a time. Run an allow and deny test after each stage.
  </Step>
  <Step title="Prove readiness">
    Complete [Verify Your Setup](/getting_started/verify_your_setup). Attach the resulting evidence and rollback record to the approved change.
  </Step>
</Steps>

## How to read a procedure

Every production procedure distinguishes between four things:

| Element | What it tells you |
| --- | --- |
| **Input** | The value required, where to obtain it, its valid form, and whether it is sensitive |
| **Action** | The smallest safe change to make |
| **Checkpoint** | The screen, output, log entry, or traffic behavior that proves the action worked |
| **Recovery** | What to inspect, reverse, or escalate when the checkpoint differs |

<Warning>
  A page marked **Pending lab validation** is useful for planning and review, but it is not approved evidence for a production change. Use only procedures that identify a verified build and review date for consequential deployment work.
</Warning>

## Documentation trust

SafeSquid documentation separates verified product behavior from architecture guidance and external standards. Product claims require reproducible evidence. Regulatory mappings describe how a control may produce evidence; they do not certify compliance.

See [How to Trust This Documentation](/reference/documentation-trust) for verification levels, ownership, update rules, and how to report an error.
